# Database and migrations

Applies to `sarpebe-backend/alembic/`, `app/db/`, and anything that changes the schema. Background: `docs/database.md`, `docs/operations.md`.

## Hard rules

- Schema changes happen only through Alembic migrations. Never edit tables by hand and never rely on `create_all` outside tests.
- Do not run `alembic upgrade` or `downgrade` against the user's database unless they asked. Read-only diagnostic `SELECT`s are fine. To check a migration without a database, render it offline: `alembic upgrade <from>:<to> --sql`.
- Never edit a migration that has already been applied or committed and shared; add a new one.
- Keep each migration reversible: write a working `downgrade()`.
- Read every autogenerated migration before keeping it. Autogenerate does not see everything (generated columns, vector and GIN or HNSW indexes, extension creation) and may drop things it does not understand.

## Workflow

1. Change the SQLAlchemy model in `app/db/models/` (and export it in `models/__init__.py`).
2. From `sarpebe-backend/`: `alembic revision --autogenerate -m "<description>"`.
3. Review and fix the file; set the correct `down_revision` (the current head). Keep one head.
4. Render offline with `--sql` and read the SQL; run `pytest`.
5. Update `docs/database.md` (ERD, columns, migration table) and `docs/configuration.md` if settings changed.
6. Tell the user which commands to run (`alembic upgrade head`, and `scripts.reindex_documents` if chunks are affected).

## Conventions

- Primary keys are UUIDs. Timestamps are timezone-aware (`TIMESTAMP(timezone=True)`), set through `app/utils/time.py` (`utc_now`).
- Foreign keys state `ondelete` explicitly (`CASCADE` for user-owned data, `SET NULL` for cost logs pointing at plans).
- New columns on existing tables get a server default or are nullable, so the migration works on populated tables. Existing plan rows must stay valid: `schema_version` defaults to 1.
- JSONB for flexible, versioned documents (`generated_content`, `request_options`, `generation_meta`, `ingest_warnings`); do not query deep into it for core logic.
- `grade_level` and `subject` are stored normalized with `normalize_label` (`app/utils/labels.py`) in `curriculum_documents` and `document_chunks`; compare them exactly.

## pgvector and search

- Embeddings are `Vector(768)`. Changing the dimension needs a migration and a full reindex.
- Always pre-filter by grade and subject before similarity or keyword ranking. Cosine distance operator `<=>`; similarity is `1 - distance`.
- Indexes: HNSW (`vector_cosine_ops`, `m=16`, `ef_construction=64`) on `embedding`; GIN on the generated `search_vector` (`to_tsvector('indonesian', chunk_content)`); btree `(grade_level, subject)`. Vector search sets `hnsw.iterative_scan` with `SET LOCAL` so filtered queries still return enough rows.
- With very few rows PostgreSQL scans sequentially; check plans with `EXPLAIN` only on realistic data.

## Query rules

- No lazy loading in list queries; use `joinedload` or `selectinload`.
- Multi-write operations in one transaction; commit before dispatching Celery tasks.
- Use `.with_for_update()` when reading and then modifying rows under concurrency (refresh-token rotation does).
- Repositories contain queries only. Ownership filters (`user_id`) belong in repository methods.
- Production connections go through the Supabase transaction pooler (port 6543).
